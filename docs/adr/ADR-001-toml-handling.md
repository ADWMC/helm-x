# ADR-001 — config.toml 处理：为什么自建行级模型

**状态**：接受
**影响范围**：`internal/codexcfg`，间接影响 `svc`（危险操作的预览与确认）
**日期**：阶段 3 开工前

## 上下文

要改写用户的 `~/.codex/config.toml`：把激活 provider 的 `base_url` 指向本地代理，并注入三个上下文默认键。
必须先备份、可原子写入、可逐字节还原（INV-6）。

真实文件的实际情况（实测本机 `~/.codex/config.toml`，173 行）：

- **58 个表头**，包含带引号的表名 `[plugins."visualize@openai-bundled"]`
- **点分表头** `[desktop.appearanceDarkChromeTheme.fonts]`，嵌套 3 层
- 顶层键与表键**同名共存**（如顶层有 `name = "hua"`，`[model_providers.1145]` 里也有 `name = "hua"`）
- 行内数组、含 Windows 路径的转义字符串
- 该文件全部是 **LF**，不是 CRLF

旧版 C++（`config.cpp:150-315`）用逐行字符串替换，已知问题：
无结构模型、依赖行的精确形态、无法可靠区分"哪个 `name` 属于哪个表"。

## 选项

### 选项 A：`github.com/BurntSushi/toml`（成熟解析器）

- ✅ 解析正确，处理全部边界
- ❌ **写回会重排格式**：注释丢失或移位、表的顺序可能变化、缩进被规范化
- ❌ 对 INV-6「可逐字节还原」是直接冲突 —— 用户配置会被无关地改动

### 选项 B：`github.com/pelletier/go-toml/v2`（保序解析器）

- ✅ 比 A 更保守，尽量保留顺序
- ❌ 仍不保证**注释与空白的逐字节保留**；写回后的 diff 不可预测
- ❌ 引入依赖（当前项目零外部依赖）

### 选项 C：自建**行级模型**（不解析值，只定位行与区间）

- ✅ 未改动的行 `bytes.Equal` 完全相同 → INV-6 可测且严格
- ✅ 零依赖
- ✅ 只需覆盖**我们真正要动的形态**：顶层 `key = value` 与 `[table]` 下的 `key = value`
- ❌ 需要自己处理行尾风格、引号、注释、表头识别
- ❌ 不适用于"完整 TOML 语义"需求（但我们没有）

## 决定

**选 C。**

理由：本项目的需求不是「读写 TOML」，而是**对用户文件做最小、可逆的点修改**。
行级模型正好匹配这个需求边界；两个成熟解析器解决的是另一个问题（完整读写），
并且会引入本项目明确不要的副作用（格式重排）与依赖。

## 后果

**必须做**：

- 行级模型只识别**结构**（表头、键行、注释、空行），**不解析值语义**
- 「值」一律作为原始字节处理，不做类型推断
- 表上下文用**栈**维护，以正确处理点分表头与引号表名
- 行尾风格（LF/CRLF）从文件探测，写入时沿用

**接受的风险**：

- 若值跨多行（TOML 多行字符串 `"""`），行级模型会误解。本机实测**未出现**该形态；
  实现时对检测到的多行值**拒绝写入并返回错误**，而不是猜
- 不处理 TOML 的 `[[array of tables]]`；同样采取"检测到即拒绝"

**验证方式**（PHASES.md 阶段 3 验收）：

- `TestByteRoundTrip`：`apply` → `remove` 后与初始**逐字节一致**
- 行级断言：改一个键，其余行 `bytes.Equal` 不变（含注释与缩进）
- 用**真实结构**（58 表 / 引号表名 / 点分表头）构造 fixture，而非简化样本
