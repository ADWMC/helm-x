## 0-A. 为什么要重做视觉：原界面确实难看，原因是可诊断的

**方法说明**：本文 v1/v2 靠读 CSS 推断视觉效果，连续错了四处。v3 起改用**截图实测**：
`msedge --headless --screenshot` 渲染 `dashboard.html`，看真实像素再说结论。

从截图（1440×1000，深色模式）读出的问题，按严重度：

| # | 问题 | 证据 | 后果 |
|---|---|---|---|
| **V1** | **首屏核心指标 3/4 是空占位** | `代理 OFFLINE / 改写器 — / TAMPER — / 提示词 —` | 落地第一屏看起来像坏了。4 格大卡片里 3 格是空横线，是整页最刺眼的东西 |
| **V2** | **一个 300×180 的模态盖在空页面上** | "你遇到了错误，是否查看 QA?" | 首访即被拦截，且遮罩把内容压暗 → 像报错页。**这是"难看"的最大来源** |
| **V3** | **两行标题说同一件事** | topbar `系统总览` + `h1 系统总览` + `p Codex 环境控制状态一览。` | 垂直空间浪费，视觉重复，且 h1 和 topbar 字号接近、层级不清 |
| **V4** | **`A. 是的 / B. 好的` 是假选择** | `dashboard.html:495` modal | 两个选项一个意思。这是设计缺陷不是文案缺陷 —— 要么给真选项（`查看 QA` / `跳过`），要么根本不该弹 |
| **V5** | 指标卡 `OFFLINE` 用 24px 红字 | `.metric strong` 24px + `.bad` danger 色 | 巨大红字占据首屏视觉焦点，实际信息量是"0/1 个服务在跑" |
| **V6** | 启用态导航是实心高饱和绿 | `.nav-button.active { background: var(--accent) }` | 与 5% 面积的品牌色争夺注意力；正确做法是低饱和底色 + 左侧指示条 |

**结论**：`web-ui` 规则 3 说"不要默认卡片+圆角+紫渐变"—— 原版没犯这个错；它犯的是**信息层级错误**：把"空"和"错误"放到了最大的容器里。

**所以重写的视觉目标不是换风格，是修层级**：

1. 首屏第一眼应该是**代理在跑 + 最近请求正常**，不是四个空指标格
2. 应用自己的空状态时，**默认无模态**。QA 从"拦截式弹窗"改成"总览页一张可关闭的提示条 + 侧边栏常驻入口"
3. 页面标题只出现一次（topbar 只留面包屑/状态，h1 留给内容区）
4. 指标值不靠字号和红色取胜，靠**位置和对比**；异常才上色

## 0. 这个软件是什么（决定设计语言的第一性约束）

不是后台管理系统，也不是落地页。是一个**常驻进程的仪表盘 + 危险操作控制台**。

三条推论，后面所有规则都由它们推出：

| 约束 | 推论 |
|---|---|
| **用户在这里看"为什么我的请求被拒了"** | 信息密度的优先级高于美观。宁可密，不可空 |
| **有些按钮会改用户的 `~/.codex/config.toml`** | 危险操作必须有明确的后果说明与恢复路径，不能和普通按钮长一样 |
| **用户看的是流式日志和实时请求** | 时间、顺序、状态变化是主信息；装饰是噪音 |

原 `dashboard.html` 的**结构**（236px sticky 侧边栏、紧凑表格、等宽日志）是对的，保留；
它的**信息层级**是错的（见 §0-A），重写要修。

## 1. 视觉语言

### 1.1 层级：一屏一个主操作

`web-ui` 规则 1。每个页面的主操作唯一：

| 页面 | 主操作 | 降级项 |
|---|---|---|
| 总览 | 无（纯状态页，只读） | 所有动作降为次级 |
| 验证 | `运行自检` | `e2e 验证` 为次级（慢、烧额度） |
| 服务 | `启动 / 停止 代理` | 重试参数、改写器开关降级 |
| 提示词 | `应用模式` | 预览提示词为只读 |
| 上下文 | `保存` | 各项阈值是次级输入 |
| QA | `检查更新` | 搜索框是工具，非主操作 |
| 改写器 | `保存并测试` | 单独的 `保存` 降级（避免两个同权重按钮） |
| 日志 | `暂停 / 跟随` | 清空为次级 |
| 请求 | 无（只读表格） | 行展开为查看详情 |

**禁止**：一个面板里两个 `btn-primary`。

**更正**：本文 v2 说"原 dashboard 没有实心主按钮"，错。原版有完整三级（`dashboard.html:136-144`）：

```css
.btn.primary   { background: var(--accent); color: var(--accent-on); }  /* 实心 */
.btn.secondary { border-color: var(--border); background: var(--bg); }  /* 描边 */
.btn.danger    { border-color: var(--danger); background: transparent; }/* 危险描边 */
```

我读漏了，因为只 grep 了 `btn-` 而原版类名是 `.btn.primary`。

**但要沿用并修正权重**：原版把 `重启服务` 这类次要动作用了 `.secondary`，而真正的主操作（如 `运行自检`）也是 `.secondary` —— 三级定义齐了却用错。新版按下表固定：

| 级别 | daisyUI | 用于 |
|---|---|---|
| 主 | `btn btn-sm btn-primary` | 每页唯一主操作（§1.1 表） |
| 次 | `btn btn-sm btn-outline` | 辅助动作 |
| 三级 | `btn btn-sm btn-ghost` | 行内、工具栏 |
| 危险 | `btn btn-sm btn-error btn-outline` | 改用户文件的操作 |

危险**不用实心填充**：原版 `.btn.danger:hover { background: var(--danger) }` 已经在 hover 时给反馈，不必常驻大红。

### 1.2 对比：主/次必须可区分

`web-ui` 规则 2。三级：

```css
btn btn-primary      /* 主：填充 */
btn btn-outline      /* 次：描边 */
btn btn-ghost        /* 三级：无边框，hover 才显形 */
```

**危险操作单独一档**，不靠颜色深浅区分：

```css
btn btn-error btn-outline    /* 恢复配置 / 移除注入 */
```

危险操作**不用 `btn-error` 实心填充** —— 实心红在深色主题下过重，且和"主操作"的视觉权重冲突，容易误点。

### 1.3 密度

`web-ui` 规则 3。这是本产品的核心：

| 区域 | 密度 | 具体 |
|---|---|---|
| 日志 / 请求表 | **密** | 单行 28–32px，等宽字体，无行间留白 |
| 设置表单 | 中 | 标签与输入同行，不上下堆叠浪费垂直空间 |
| 页面头部 | 松 | 标题 + 一句话说明，然后立刻进内容 |

**禁止**：卡片套卡片（`card` 里再放 `card`）；大留白的欢迎区；把 3 个数字做成三个大卡片占据整屏（用 `stats` 一行解决）。

### 1.4 状态不能只靠颜色

`web-ui` 规则 6。这对本产品是硬要求 —— 判定状态是核心信息。

**更正**：本文 v1 用 `✓ / ! / ✕` 当图标，这是错的。原版 `dashboard.html:275、336、627` 的既有约定是**彩色圆点 + 文字**：

```html
<span class="status done"><span class="status-dot"></span>REGEX</span>
```

```css
.status-dot { width: 6px; height: 6px; }   /* 颜色由 .done/.running/.error 决定 */
.status.error { color: var(--danger); border-color: var(--danger); }  /* 文字也变色 */
```

对钩/叉号在密集表格里视觉噪音大，且和 `.status` 的圆点语言不一致。**沿用圆点**，并补齐原版缺的部分 —— 圆点只有颜色、没有形状差异，色盲用户读不出：

```
● 正常          实心圆 + 成功色
● 已改写        实心圆 + 警告色
● 已重建会话     实心圆 + 错误色
○ 上游失败      空心圆 + 错误色   ← 形状差异补色盲可读性
◌ 无法解析      空心圆 + 中性色
◐ 未补救        半填充 + 警告色   ← 最需要被看见的状态
```

色盲模拟下 `●/○/◐` 可区分。这是对原版约定**做加法**，不是替换。

**判定状态词固定中英对照**：

| 内部 Class | 界面词（中） | 界面词（英） | 含义 |
|---|---|---|---|
| `Healthy` | 正常 | Passed | 原样转发 |
| `Refused` | 已改写 | Rewritten | 命中拒绝规则，已补救 |
| `Flagged` | 已重建会话 | Resent | cyber flag，换会话重发 |
| `UpstreamFailed` | 上游失败 | Upstream failed | 未拿到有效响应 |
| `Malformed` | 无法解析 | Unparsed | 响应形态不认识，原样透传 |
| `Unresolved` | 未补救 | Unresolved | 三级补救全失败，原样返回（§5.5） |

`Unresolved` 必须显式存在。这是 INV-8 的界面承诺：**补救不了就直说，不能假装成功**。

## 2. 组件边界（对齐业务角色，不对齐工具类名）

`web-ui` 规则：组件边界对齐业务角色。

**不要**建 `Card.vue` / `Button.vue` / `Input.vue` 这类对 daisyUI 的薄包装 —— 那样只是多一层间接，没带来任何约束。

**要**建真正承载业务语义的组件：

| 组件 | 承载的业务概念 | 关键约束 |
|---|---|---|
| `VerdictBadge` | 一次请求的判定结果 | 唯一消费 `useVerdictStyle`；禁止外部传颜色 |
| `RequestRow` | 请求表的一行 | 只读；展开才加载详情（避免拉全量） |
| `LogStream` | 实时日志 | 自动滚动可暂停；暂停后新行不丢（缓冲计数） |
| `StatTile` | 单个指标 | 值 + 单位 + 一句话上下文，不给裸数字 |
| `ServiceToggle` | 一个后台服务的启停 | 内含"运行中/已停止"状态，不允许外部只传 `disabled` |
| `ConfigField` | 一个写入 `config.toml` 的字段 | 必须显示"当前值 / 将写入值 / 影响哪个文件" |
| `DangerZone` | 会改用户文件的操作集合 | 独立视觉区块，内含后果说明与恢复路径 |

后两个是本项目特有的：普通后台不需要告诉用户"我要改你哪个文件"。

## 3. 交互规则

### 3.1 危险操作

改 `~/.codex/config.toml` 的操作（`apply` / `remove` / 改 base_url / 改上下文默认值）走固定流程：

```
触发
 └─ 弹 modal，逐条列出：
      · 会改哪个文件（绝对路径）
      · 改什么（具体键、旧值 → 新值）
      · 备份在哪（.helmx-bak / .helmx-proxy-bak）
      · 怎么撤销（界面按钮 + 手动做法）
 └─ 确认按钮用 btn-error btn-outline，文案是动词："应用并备份"
 └─ 执行 → 结果用 alert 呈现，成功也显示实际写入的路径
```

**禁止**：`确定 / 取消` 这种无信息量的按钮。文案 `anti-slop` 规则：按钮写动作。

### 3.2 长任务

自检、e2e 验证、改写器测试是秒到分钟级。规则：

- **立即返回**，界面显示进度（`progress` + 当前步骤名）
- 可取消；取消后显示已完成的部分，不假装什么都没发生
- 完成后结果**留在页面上**，不自动消失（用户可能要复制报告）
- 切走页面再回来，任务状态不丢（事件驱动，不是页面局部状态）

### 3.3 实时流

日志与请求表：

- 默认**跟随**（自动滚到底）
- 用户手动上滚 → **自动暂停跟随**，显示 `已暂停 · N 条新记录`，点击回到底部恢复
- 暂停期间数据不能丢（这是原版轮询模式做不到的，也是引入事件推送的理由之一）
- 上限保留 N 条（默认 2000），超出丢弃最旧的，并在列表顶部标注 `仅显示最近 2000 条`

### 3.4 空状态与错误

空状态必须说**下一步做什么**，不是干说"暂无数据"：

| 场景 | 文案 |
|---|---|
| 无请求记录 | `还没有请求经过代理。确认 codex 的 base_url 指向 http://127.0.0.1:1800/v1 后发一条消息。` |
| 未找到 codex 配置 | `未找到 config.toml。设置的 CODEX_HOME 或先运行一次 codex。` |
| 改写器未配置 | `改写器未启用。当前拒绝只能靠 TAMPER 改写，无法重建会话。` |
| 上游失败 | `上游返回 <状态码>。已重试 <N> 次。检查中转地址与密钥是否有效。` |

错误文案 = 发生了什么 + 下一步（`anti-slop` 规则）。

### 3.5 键盘

这是仪表盘，键盘效率是真实需求：

| 键 | 行为 |
|---|---|
| `1`–`9`, `0` | 切换页面（顺序同侧边栏） |
| `/` | 聚焦当前页的搜索/过滤 |
| `Esc` | 关闭 modal / 清除搜索 |
| `Space` | 日志页：暂停/跟随 |

**不做**命令面板（`Ctrl+K`）。10 个页面、单层结构，数字键更快，做面板是给想象需求搭架子。

## 4. 文案规则

### 4.1 语气

技术、直接、不劝。用户是拿这个工具排查问题的人，不需要被安慰。

**禁止**（`anti-slop`）：强大 / 无缝 / 极致 / 重新定义 / 智能 / 一键搞定。

### 4.2 术语一致性（硬约束）

三套词汇必须严格对应，不许出现第三种说法：

| 代码 | 界面 | 禁止的说法 |
|---|---|---|
| proxy | 代理 | 中间件、网关、MITM 服务 |
| inject | 注入 | 植入、写入指令 |
| TAMPER | 改写 | 篡改（文档里可以，界面不用）、替换、过滤 |
| rewriter | 改写器 | 重写器、rephrase 服务 |
| clean session | 重建会话 | 新会话、清空历史 |
| upstream / relay | 上游 | 后端、远端、目标服务器 |
| cyber flag | 安全标记 | 风控、审查 |
| ~~context gardener~~ | ~~上下文裁剪~~ | **已废弃**：功能实测空转，已从产品移除 |

**"改写"一词有两义**，必须靠上下文限定：`TAMPER 改写`（正则，确定性）vs `改写器改写`（LLM，语义）。界面上一律带限定词，不裸用"改写"。

### 4.3 数字与时间

- 字节：`1.2 KB` / `340 B`（1024 进制，后缀与数字间空格）
- 时长：`420 ms` / `1.4 s`
- 时间戳：`14:32:07`（当天）/ `08-14 14:32`（跨天）
- 百分比保留一位小数：`93.9%`（这是项目的基线数字，必须精确）

## 5. 主题与色板

### 5.1 基调：跟随系统

**更正**：本文 v1 断言"原控制台是深色"，v2 又断言"默认浅色"。两次都是靠读 CSS 猜的。

**实测**（`--headless --screenshot`，1440×1000）：token 里 `--bg: #ffffff`（第 10 行）确实是浅色默认，但 headless 环境 `prefers-color-scheme` 为 dark，所以渲染出深色。**两种都真实存在。**

事实是：原版是**跟随系统的双模式**（`:root` 浅色 + `html.dark-mode` 深色，由 `prefers-color-scheme` 切换，`dashboard.html:524-525`）。

新版保持一致 —— **两套都做，都要截图验证**：

```css
@plugin "daisyui" {
  themes: light --default, dark --prefersdark;
}
```

> 教训：判"默认是什么"不能只看 token 声明，要看运行时实际渲染。

### 5.3 主题切换

**决定：跟随系统，不提供手动选择器。**

原版就是这个行为，且没有任何切换 UI。不开放 daisyUI 内置的其余 33 套主题 —— 视觉验证成本 ×N，收益为零。

（`PLAN.md` §9 第 7 条据此关闭。）

### 5.2 语义色映射（唯一一处）

```ts
// composables/useVerdictStyle.ts —— 全项目唯一的判定→样式映射
// dot 用形状而非仅颜色（§1.4）；text 让色盲与黑白截图可读
const VERDICT: Record<Class, { dot: string; text: string; label: string }> = {
  Healthy:        { dot: '●', text: 'text-success',  label: '正常' },
  Refused:        { dot: '●', text: 'text-warning',  label: '已改写' },
  Flagged:        { dot: '●', text: 'text-error',    label: '已重建会话' },
  UpstreamFailed: { dot: '○', text: 'text-error',    label: '上游失败' },
  Malformed:      { dot: '◌', text: 'text-base-content/60', label: '无法解析' },
  Unresolved:     { dot: '◐', text: 'text-warning',  label: '未补救' },
}
```

**业务组件禁止自己判断颜色**（`PLAN.md` §5.9 约定的落地）。要加状态就改这一处。

## 6. 无障碍

最低线，不是加分项：

| 项 | 要求 |
|---|---|
| 对比度 | 正文 ≥ 4.5:1；`badge` 上的文字单独核对（深色主题下小字号易踩线） |
| 焦点可见 | 所有可交互元素有 `focus-visible` 环；不可 `outline: none` 了事 |
| 键盘可达 | 表格行、按钮、tab 全部可 Tab 到达；modal 内焦点锁定 |
| 状态 | 不只用颜色（§1.4；原版圆点只有颜色，新版补形状） |
| 动效 | 尊重 `prefers-reduced-motion`，关闭日志滚动动画 |

**注意**：`prefers-reduced-motion` 在原版里**已经处理**（`--motion-base: 220ms` + `--ease-standard`，见 `dashboard.html:45-47`），新版在 daisyUI 下要重新接上，不能因为换库丢掉。

## 7. 布局骨架

**更正**：本文 v1 画的"侧边栏 + 内容区 + 常驻底栏"三段式是错的。原版是**两段式**（`dashboard.html:75`）：

```css
.app-shell { display: grid; grid-template-columns: 236px minmax(0, 1fr); }
```

侧边栏信息在**侧边栏底部**（`.sidebar-foot`：版本号 + config 路径），不是横跨底部的底栏。滚轮向下时侧边栏是 `position: sticky; height: 100vh`，始终可见。

保持这个结构：

```
┌──────────┬────────────────────────────────────────┐
│ brand    │  页面标题 + 一句话说明        [主操作]   │  ← topbar: sticky, 56px, 半透明毛玻璃
├──────────┼────────────────────────────────────────┤
│ 10 项导航 │                                        │
│ (可分组)  │  内容区（面板垂直流）                    │
│          │                                        │

原版首屏（§0-A V1/V3/V5）把 4 个等宽指标格放在最显眼的位置，而运行时常有 3 个是占位符。新版改结构：

│  │ 14:32:07  POST /v1/responses   12.4 KB  ● 正常  420ms │   │  ← 真实数据优先

│  └───────────────────────────────────────────────────────┘   │
│                                                              │
│  ┌ 改写器 ─────┐ ┌ TAMPER 规则 ─┐ ┌ 提示词 ──────┐          │  ← 指标降级到下方
│  │ 已启用       │ │ 26 条        │ │ ctf-scoring  │          │
│  └─────────────┘ └──────────────┘ └──────────────┘          │
└──────────────────────────────────────────────────────────────┘
```

三条规则：

1. **主状态条唯一**：代理在跑/没跑，一屏只有一个地方说这件事，用 §1.4 的圆点语言。
2. **真实数据优先**：有请求记录就显示"最近请求"，没有才显示空状态文案（§3.4）。**不允许在没有任何数据时用大卡片占位。**

### 7.2 页面标题只出现一次

修 V3。规则：

- **topbar** 只承载：移动端汉堡按钮 + 当前页名（小号，作面包屑）+ 右侧全局状态
- **内容区 h1** 承载页面标题，字号 `text-2xl`
- 两者**不得同字**。原版两处都写"系统总览"，删掉 topbar 那份，改为面包屑形式 `概览 / 系统总览` 或直接留空

### 7.3 取消拦截式欢迎模态

修 V2/V4。原版首访弹 `你遇到了错误，是否查看 QA?` + `A. 是的 / B. 好的`（两个选项同义）。

新版：

- **删除该模态**
- QA 入口常驻侧边栏（原版已有 `QA 帮助` 项）
- 首次运行改为**总览页一张可关闭的提示条**：`新用户？这里整理了常见错误和处理方法。[查看 QA] [不再提示]`

## 12. 深色配色重做（用户反馈"要黑不黑 要灰不灰"）

### 12.1 问题定位

用户的原话是四个字：**"要黑不黑 要灰不灰"**。查了构建产物，确认不是主观感受：

原实现直接用 daisyUI 的 `dark` 默认值：

```
--color-base-100: oklch(25.33% .016 252.42)   ← 中灰
--color-base-200: oklch(23.26% .014 253.1)
--color-base-300: oklch(21.15% .012 254.09)
```

两个毛病：

1. **不是黑，是 25% 明度的灰蓝。** 深色界面用中灰做画布，观感就是"脏"。
2. **三层只差 2 个百分点**（25.33 / 23.26 / 21.15），在深色下几乎读不出层级 ——
   卡片和画布糊成一片，这正是"灰"的来源。

### 12.2 参照系

用 `VoltAgent/awesome-design-md` 里经过市场验证的深色系统做对照：

| 系统 | canvas | surface | hairline |
|---|---|---|---|
| Linear | `#010102` | `#0f1011` / `#141516` | `#23252a` |
| Raycast | `#07080a` | — | `#242728` |
| Warp | `#2b2622`（暖调，未采用） | — | `#3f3a36` |

**共同点**：画布接近纯黑，靠"表面提亮"而非"画布压灰"来建立层级，
且层级之间拉开足够步长。

### 12.3 改成什么

```
base-100  oklch(8%  .008 250)   画布（近黑，极轻冷调）
base-200  oklch(13% .01  250)   卡片 / 面板
base-300  oklch(20% .012 250)   边框 / 分隔
```

8 → 13 → 20 的步长能明确读出三层。另外两处一并调整：

- **正文不用纯白**（`oklch(96%)`）：纯白在近黑底上对比过强，长时间看会累。
  Linear 同样用 `#f7f8f8` 而非 `#ffffff`。
- **语义色提亮**：success/warning/error/info 在近黑底上需要更高明度才够对比，
  分别为 72% / 80% / 70% / 72%。

### 12.4 验证方式

**不能只查 CSS 文本** —— 第一次就是从产物里 grep 主题变量，
结果匹配到了另一个选择器块，误判为"没生效"。CSS 里同名变量会出现多次
（默认主题、`[data-theme=X]`、`@media(prefers-color-scheme:dark)`），
文本检索天然不可靠。

只认渲染结果：截图 + 从活页面读 computed style。

---

### 12.5 分割线不可见的修复

**用户反馈**："分割线呢"。

**像素诊断**（直接从 CDP 截图读取渲染结果，不是看 CSS）：

| 位置 | 修复前 | 修复后 |
|---|---|---|
| 页面背景 | `#121212` (18,18,18) | `#121212` (18,18,18) |
| 边框 | `#12171B` (18,23,27) | `#20252A` (32,37,42) |
| 卡片内部 | `#020305` (2,3,5) | `#05080B` (5,8,11) |
| 页面→边框亮度差 | **5** | **18** |

两个原因：

1. **卡片用了和页面同色的 `bg-base-100`** —— 卡片背景与画布完全相同，看不出"浮起来"。
   改为 `bg-base-200`（面板色）。

2. **边框 `base-300` 只有 20% 亮度** —— 与 `base-100`(8%) 只差 12 个百分点。
   在近黑底上这几乎不可见。提到 **26%**，与卡片边框形成清晰分界。

**修复文件**：
- `components/SectionCard.vue`：`bg-base-100` → `bg-base-200`
- `style.css`：`base-100` 从 8% → 7%，`base-300` 从 20% → 26%

**教训**：CSS 里"有 border"不等于"看得见 border"。在近黑底上，亮度差 <10 个百分点就等于没有。

### 12.6 按 Linear 四层 surface 阶梯重做

**用户反馈**："界面完全不分明"。

**问题**：之前只有 3 层 surface，且层间差太小（12 个百分点）。
卡片用 `bg-base-100`（和页面同色），边框对比度低，
导致整个界面糊成一片，看不出层级。

**参照 Linear 的做法**（VoltAgent/awesome-design-md）：

```
canvas      #010102   页面底色（近黑）
surface-1   #0f1011   卡片 / 面板（比底亮 5%）
surface-2   #141516   提升卡片（比 surface-1 亮 3%）
surface-3   #18191a   嵌套元素
hairline    #23252a   边框（比底亮 14%）
```

核心原则：**靠 surface 色阶本身分层，不是靠边框**。
边框只做细微点缀（1px hairline），真正的层级感来自背景色差异。

**改为**：

| 层级 | 用途 | oklch |
|---|---|---|
| base-100 | 页面画布 | 6% |
| base-200 | 卡片 / 面板 | 12%（+6 个百分点） |
| base-300 | 边框 / 分隔 | 22%（+16 个百分点） |

**同时给 daisyUI 组件补上分层**：
- `.card` → `base-200`（卡片浮起来）
- `.modal > .modal-box` → `base-200`（浮层比页面亮）
- `.input/.select/.textarea` → `base-100`（输入框与页面连续）
- `.table thead` → `base-200`（表头区分于行）
- `aside` → `base-200`（侧边栏与内容区同级但有边框分隔）

**验证**：截图对比，三张卡片（代理、自愈守护、配置注入）
现在有清晰的边框和浮层感，视觉层级一目了然。

### 12.7 降低对比度（用户："辣眼睛"）

**问题**：上一版按 Linear 四层 surface 阶梯重做后，对比度仍然过高。

**根因**：我用的值比 Linear 实际值亮得多：

| 层级 | Linear 实际 | 我上一版 | 差距 |
|---|---|---|---|
| canvas | `#010102` ≈ 0.4% | `oklch(6%)` | 亮 15 倍 |
| surface-1 | `#0f1011` ≈ 6% | `oklch(12%)` | 亮 2 倍 |
| hairline | `#23252a` ≈ 14% | `oklch(22%)` | 亮 1.5 倍 |

**改为按 Linear 实际值**：

| 层级 | 用途 | oklch | 对应 hex |
|---|---|---|---|
| base-100 | 页面画布 | 1% | ≈ `#010102` |
| base-200 | 卡片 / 面板 | 6% | ≈ `#0f1011` |
| base-300 | 边框 / 分隔 | 14% | ≈ `#23252a` |

同时降低文字和语义色的饱和度，让整体更柔和。

**教训**：Linear 的"深色"是真的**深**（canvas 几乎纯黑），
不是"深灰"。我之前把 canvas 设成 6% 已经太亮了。
真正的近黑设计，canvas 应该在 1% 以下。

### 12.8 暖色调深色主题（参照 Cursor）

**用户反馈**："纯黑有点难受了"。

**参照 Cursor 的理念**（VoltAgent/awesome-design-md）：

> Warm cream canvas, not white. Ink is warm (#26251e), not pure black.

Cursor 的色调是**暖的**：
- canvas `#f7f7f4` 暖米白（不是纯白）
- ink `#26251e` 暖近黑（不是纯黑）
- hairline `#e6e5e0` 暖灰

翻译到深色：
- 之前用 hue 250（冷蓝），纯黑 OLED 屏看了难受
- 改为 hue 60（暖橙），canvas 从 1% 提到 3%（略高于纯黑）

| 层级 | 用途 | oklch | sRGB 实际 | 色调 |
|---|---|---|---|---|
| base-100 | 页面画布 | 9% hue 60 | ≈(3,2,2) | 暖炭黑 |
| base-200 | 卡片 / 面板 | 14.5% hue 60 | ≈(25,21,18) | 暖深灰 |
| base-300 | 边框 / 分隔 | 20% hue 60 | ≈(22,19,17) | 暖灰 |

正文改为 `oklch(93% 0.004 60)` 暖白，不用纯白。

**教训**：深色主题不一定要"冷"。Cursor 证明暖色调的深色
更舒适，尤其是长时间盯着界面时。色相选择（暖 vs 冷）
和亮度一样重要。

**教训 2（v4 实测）**：oklch 亮度在近黑段必须换算成 sRGB 再评审。
oklch 3% 与 6% 渲染出来是 rgb(0,0,0) 与 rgb(1,1,0)——差 1 个
sRGB 台阶，卡片和画布肉眼不可分（v3 "界面不分明"的根因之一）。
且 oklch ≤3% 时暖色相根本显不出来（数值贴着 0）。上表 sRGB 列
才是可感值；层级台阶要按 sRGB 差值设计（画布→卡片 ≈ 10-20）。

## §13 设计系统 v4：Apple 材质 / 排版 / 动效

按 apple-design 技能重做（2026-10-03）：

**材质（§12）**
- 顶栏/侧栏/弹窗 = 毛玻璃浮层（`backdrop-filter: blur() saturate()`），
  内容从底下滚过；受光边（inset 亮线）模拟真实材料
- 卡片 = 双层投影（小投影定形 + 大投影托浮）+ 发丝线边框
- 弹窗进场 = 材质化（scale + blur + opacity 一起动），不是纯淡入
- 页面画布必须显式给 body 上色，否则漏出 WebView2 默认画布色

**排版（§15）**
- `.display`：大标题负字距 -0.022em + 紧行高 1.12
- `.eyebrow`：小标签正字距 0.09em + uppercase
- 数字等宽（tabular-nums）全局

**动效（§1/§4/§14）**
- 按压反馈在 pointer-down 即时发生：`.btn:active → scale(0.97)`
- 缓动统一 `--ease-spring: cubic-bezier(0.22,1,0.36,1)`（临界阻尼弹簧
  的 CSS 近似，无过冲；本应用无甩动手势，不过冲）
- 页面切换：进场弹簧 280ms / 退场快淡 120ms，进出同路径
- `prefers-reduced-motion` 全关位移；`prefers-reduced-transparency`
  毛玻璃降级为实底

**分隔线取舍**：apple-design 倾向"滚动边缘渐隐而非硬分割线"，
但用户此前明确要求保留分割线（"分割线呢"）——保留发丝线
（rgba 白 4.5%-7%），只在浮层与内容重叠处用材质本身区分。
